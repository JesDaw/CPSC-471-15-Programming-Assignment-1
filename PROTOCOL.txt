=====================================================================
 Simplified FTP - Application-Layer Protocol Design
=====================================================================

1. OVERVIEW
-----------
Two TCP connections are used per session:

  CONTROL channel - opened by the client to the server's well-known port.
                    Lives for the whole session. Carries every command
                    (ls / get / put / quit) from client to server and every
                    status / error reply from server to client.

  DATA channel    - created for each ls / get / put and torn down when
                    that transfer ends. The CLIENT picks an ephemeral port
                    (bind to port 0), listens on it, and tells the server
                    the port number over the control channel. The SERVER
                    then connects to that port on the client.

2. MESSAGE FORMAT (framing)
---------------------------
TCP is a byte stream: send() may send fewer bytes than asked and recv() may
return fewer than asked. Every message is therefore length-prefixed, and both
sides loop on send()/recv() until all bytes have moved.

  Control message:  [10-byte ASCII length, zero padded][UTF-8 text payload]
                    e.g. "0000000012" + "get 40123 a.txt"-style payloads.

  Data channel:     [10-byte ASCII length, zero padded][raw bytes]
                    The receiver reads the 10-byte header, then loops on
                    recv() until exactly that many bytes have arrived. This
                    is how the receiver knows when to stop (no end-of-file
                    marker, so binary files are safe). Data is moved in
                    64 KB chunks so a file is never held fully in memory and
                    TCP send buffers are never overrun.

3. CONTROL MESSAGES
-------------------
Client -> Server (text payload):
    ls   <port>
    get  <port> <filename>
    put  <port> <filename>
    quit

Server -> Client:
    OK            request accepted; server is about to open the data channel
    ERR <reason>  request rejected, or transfer failed
    DONE <bytes>  transfer finished successfully (always the last message of
                  a successful command)

Error reasons include: unknown command, malformed request, invalid file name,
file not found, and I/O / data-connection failures.

4. MESSAGE EXCHANGE
-------------------
Control channel is already open. For  get <file>  (put and ls are identical
apart from the direction of the data and the absence of a filename for ls):

  Client                                         Server
    | bind(0), listen -> ephemeral port P          |
    |---- "get P file" (control) ----------------->|
    |                                              | check file exists
    |<--- "OK" or "ERR file not found" (control) --|   (on ERR: stop here)
    |                                              |
    |<=== server connect()s to client:P (data) ====|
    |<=== 10-byte size + file bytes (data) ========|   (put: client -> server)
    |  data connection closed by both sides        |
    |<--- "DONE <bytes>" (control) ----------------|
    |  client prints filename + bytes              | server prints SUCCESS

  quit:   client sends "quit", server replies "OK", both close control.

The server logs SUCCESS or FAILURE for every request. The client prints the
file name and number of bytes after every completed get/put.

5. DESIGN DECISIONS
-------------------
* Status before data: the server replies OK/ERR on the control channel
  BEFORE any data connection is made, so a missing file never leaves the
  client waiting for a data connection.
* Final DONE message: the client knows the transfer fully completed on the
  server side, and the control channel stays in sync for the next command.
* Server-initiated data connection: follows the assignment (and classic
  active-mode FTP). The server uses the control connection's peer address as
  the client's IP, so only the port is sent.
* Safety: file names containing path separators ("../x") are rejected;
  uploads are written to <name>.part and renamed only once complete, so a
  failed transfer never leaves a truncated file behind.
* Concurrency: the server runs one thread per client session.
* ls output is generated with os.listdir (no shell), so there is no command
  injection risk.

6. LIMITS
---------
Because the server connects back to the client, a client behind NAT or a
firewall that blocks inbound connections cannot receive the data channel
(same limitation as active-mode FTP). Works on localhost and on the lab
network.
